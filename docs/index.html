AutoDraft

A desktop app that takes the administrative work out of preparing client documents. A client fills out one form, and AutoDraft generates every document in the package, each one built to match that client's answers.

One template, filled from one form submission. Static fields Dynamic fields repeat once for each matching answer.

  • 3services
  • 6API resources
  • 1form per client

Overview

AutoDraft is a work in progress and is not a production deployment. No live databases, storage buckets, or Cloudflare Workers are provisioned for it, and parts of the interface use sample data. The project demonstrates the design and engineering of an application built to grow into a large-scale production system.

Preparing a document package, such as a will set with a Last Will & Testament, Powers of Attorney, a HIPAA Release, and a Living Will, usually means typing the same client details into many documents by hand and then adjusting each one to the client's situation. AutoDraft automates that work from template to finished document.

How it works

  1. Upload templates

    Choose .docx templates with the file browser or drag them into the upload window.

  2. Scan for fields

    The Electron main process reads each template and collects every {{Category | Field}} placeholder, sorting them into static and dynamic fields. The scan window updates after each file.

  3. Configure fields

    In the field editor, detected fields are organized into sections and mapped to questions on the client form.

  4. Build document sets

    Templates that are always prepared together are grouped into a set, in the order they should be generated.

  5. Collect the client's answers

    The client fills out a single JotForm form. Each submission appears in the app under that client.

  6. Generate

    The answers are patched into every document in the set. Conditional logic includes or leaves out content, so each document holds only what applies to that client.

Writing templates

Templates are ordinary Word documents with placeholders where client details belong. A placeholder has a category and a field name, separated by a pipe and wrapped in double braces:

Placeholder syntax
{{Category | Field}}

Category and field names use letters, the digits 1 to 9, and single spaces. The spaces around the | are required.

Static fields

A static field has one value per client. Every copy of it in every document gets the same answer.

Template
This Will is made by {{Client | Full Name}}, residing at {{Client | Address}}.

Dynamic fields

A dynamic field repeats. Add a * as the last word of the category, and AutoDraft fills it once for each matching entry on the form, replacing the * with that entry's number. One placeholder covers one child or ten.

Template
Guardian of {{Child * | Name}}: {{Child * | Guardian}}
Form answers it reads
Child 1 | Name      Avery Rivera
Child 1 | Guardian  Morgan Lee
Child 2 | Name      Sam Rivera
Child 2 | Guardian  Morgan Lee

Which entries are included is decided by conditions: a dynamic section is generated only when the form answer it depends on matches. Each template's file name is stored with its fields so conditions can target a specific document.

Templates are never committed. They contain proprietary content, so .gitignore excludes them along with every .doc and .docx file. To try field detection, put your own templates in frontend/src/data/templates/.

Architecture

AutoDraft is a monorepo with three services. The desktop app does the document work locally, the REST API owns accounts and metadata, and a Cloudflare Worker guards file storage.

IPC bridge

The renderer has no Node access. Everything that touches the file system, the network, or Word files goes through one preload bridge, window.ipcAPI. Its TypeScript type comes straight from the preload object, so the renderer and main process can't drift apart.

REST API

An Express 5 server with Mongoose models, split across separate MongoDB databases for users, metadata, and documents. Passwords are hashed with bcrypt.

Storage worker

Template files live in Cloudflare R2 behind a Worker. Every request has to carry three headers, and the Worker rejects it before routing if any check fails:

  • X-Filename: the file being read or written
  • X-Timestamp: when the request was signed. Requests older than five minutes are refused, which blocks replays.
  • X-Signature: an HMAC of filename:timestamp, made with a secret shared only with the backend

Signed requests can then POST /files/postFile, GET /files/getFile, or DELETE /files/deleteFile.

Running locally

Since nothing is deployed, running the full system means bringing your own services: a MongoDB Atlas cluster, a Cloudflare account with an R2 bucket, and a JotForm API key. The desktop app's interface runs without them, using sample data. You'll need Node.js and npm.

  1. Clone the repo:
    bash
    git clone https://github.com/ChrisRaiz/AutoDraft.git
cd AutoDraft
  2. Start the desktop app:
    bash
    cd frontend
npm install
npm start

    Use npm run package to build a distributable app.

  3. Start the REST API, in a second terminal:
    bash
    cd backend
npm install
npm start
  4. Run the storage worker with Wrangler:
    bash
    cd r2-worker
npm install
npm run dev
